# 1、Skill 数量增多，Agent 命中率如何保证？

先把「命中」定义清楚：该调用时选对 Skill，不该调用时不误触发。可以从四步入手：

1. **写清适用边界。** 描述 Skill 能做什么、什么时候用，以及哪些容易混淆的请求不该用。比如「我的订单到哪了」应该触发「查订单状态」，即使「取消订单」也包含“订单”这个关键词。
2. **缩小候选范围。** 可以按研发、运营等类别做粗筛。类别明确时优先查对应分区，类别不明确时允许跨类召回。再用关键词或语义检索找候选，对候选排序后取前 K 个。
3. **结合上下文做最终选择。** 让模型根据当前请求和对话上下文选 Skill。没有合适的候选时允许不调用，意图不明确时可以先问一句。
4. **用标注样本验证。** 用容易混淆的请求和无需调用 Skill 的请求做评估。看正确 Skill 有没有进前 K 个候选（Recall@K）、该调用时最终选对了多少，以及不该调用时有多少被误触发。命中率下降时，先区分是召回漏了，还是召回后选错了。

# 2、Agent的RAG遇到PDF，应该怎么处理？

**真实的PDF远比文字复杂**：
- **多栏排版**：文字顺序，穿插混乱
- **表格数据**：财务报表，统计图表
- **扫描件**：纸质图像，手写字体
- **页眉页脚**：干扰信息，噪声

可以从以下几步入手：

1. **页面向量化。** 将 PDF 按页渲染成图片，使用 ColPali 等模型对页面进行编码，再根据用户的问题匹配相关页面。[ColPali](https://arxiv.org/pdf/2407.01449)
2. **保留元信息。** 切块后保留页码、页眉页脚和标题层级等信息。对于表格，保留表格标题和表头。
3. **给 chunk 补充上下文。** 标明每个 chunk 所属的章节，并简要说明它前后的内容在讲什么。
4. **让 Agent 按需调用 PDF 工具。** 查找相关片段时用 `search_pdf`，查看指定页面时用 `read_page`，抽取表格时用 `extract_table`，获取引用来源时用 `quote_source`。简单的事实类问题可以直接走语义召回，具体场景待补充。
5. **通过溯源减少幻觉。** 在前端展示引用来源，要求回答以检索到的材料为依据。信息不足时，可以说明缺少什么或向用户追问。评测时检查每条引用是否指向正确的章节和页码。

# 3、大模型怎么稳定输出JSON？

分为以下四层：

1. **提示词规约**：直接将Schema放入Prompt，定死字段和类型，并提供2-3个正例子。由于近因效应，要把这些写到prompt的后端。
2. **生成控制**：闭源API，JSON Mode/Structured Outputs。开源模型私有化部署，Logit Masking，预测下一个词的时候将不合法的数据写成负无穷。
3. **工程校验和修复**：Pydantic强校验，对于缺括号等小瑕疵可以先用JSON Repair做修复，如果还不行，把报错信息输入给大模型重新生成。如果在生成过程中发现字段不匹配，可以直接打断重来，节省token以及时间。
4. **终极手段**：SFT监督微调。


# 4、Skill上线之后，你怎么持续维护？

首先定义目标是什么，怎么判断是否是好的。
- **结构目标**：最通俗易懂，改完Skill后还是否能正常完成工作。
- **过程目标**：Agent是否按照预想的链路进行执行，验证行为路径，并不仅仅是重点。
- **风格目标**：输出规范（文件结构，代码风格）是否能被下游消化？
- **效率目标**：是否乱调用工具，有无意义的token消耗。
